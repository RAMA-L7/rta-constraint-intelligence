Trust Center

Precision about what we validate

A tool that tells you what it does NOT do is more trustworthy than one that implies everything. This page is the complete trust model — statuses, non-claims, security and known limitations.

Trust model

Every construct gets one of six statuses

The validator never silently assumes correctness. Each analyzed construct is classified into a documented trust status.

VALIDATED

Fully analyzed within the supported boundary: syntax, semantics, structure and references proven.

PARTIALLY VALIDATED

Analyzed, but parts of the construct fall outside value-analysis (options present but not value-checked).

NETLIST REQUIRED

Object references (get_ports / get_pins / all_*) cannot be proven without a structural netlist.

TCL EXECUTION REQUIRED

Constructs whose meaning requires Tcl execution the validator deliberately does not perform.

UNSUPPORTED

Outside the documented support boundary — reported explicitly, never assumed correct.

NOT VALIDATED

Not checked by this run — the trust scope panel always lists what was not analyzed.

What we validate

Deterministic structural and semantic analysis

  • SDC syntax and command semantics within the supported subset
  • Clock definitions: primary, generated, virtual; ancestry and relationships
  • Semantic references: clock names, objects, collections
  • Constraint interactions: duplicates, overrides, contradictions, overlaps
  • Design-aware coverage when a netlist is supplied
  • Readiness across seven evidence-backed dimensions
  • Regression: snapshot baselines and semantic diff

What design context enables

Object resolution, not timing

With a structural Verilog netlist, references resolve against real objects; hierarchy, ports, pins, cells and nets become checkable evidence; NETLIST_REQUIRED constructs upgrade to VALIDATED where they resolve.

◈Design context is a structural inventory. It does not compute timing, delay or slack.

Non-claims

What we explicitly do not do

These boundaries are features. A READY verdict and a green CI gate mean specific, documented things — and never these:

✗ No STA signoff

This product does not replace PrimeTime, Tempus or any signoff STA engine.

✗ No slack calculation

No setup/hold slack, no path delays, no arrival times.

✗ No .lib timing analysis

Library timing models are outside the analysis boundary.

✗ No physical timing

No parasitic, RC, clock-tree or physical timing analysis.

✗ No closure guarantee

100% coverage does not mean correct timing intent; READY does not mean timing closes.

✗ No AI runtime

Validation is deterministic and offline. AI may be used to develop the product — never to validate your constraints.

Security / local processing

Your constraints stay on your machine

Validation runs locally. The wheel has no network imports, no external API calls, no telemetry. HTML reports escape user content (the stored-XSS fix is regression-tested). CUSTOM policies are declarative data — no eval or executable logic in the runtime.

✓Offline operation — clean-room checks verify no network imports
✓Escaping tested — adversarial <script> content renders escaped
✓No telemetry — nothing phones home
