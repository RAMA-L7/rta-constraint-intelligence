Where it fits

Constraint development → validation → STA. The missing step.

SDC files grow complex fast: generated clocks, cross-domain pairs, wildcard drift, duplicate constraints, delays that silently exceed their clock period. By the time STA runs, small constraint defects waste hours of signoff iteration.

Ṛta sits between constraint authoring and STA — catching structural and semantic problems with a deterministic engine, so the constraint set that reaches timing analysis is one you can defend.

What the product does

Five pillars, one deterministic engine

01 / VALIDATE

Check constraints

  • Deterministic rule engine — 100+ documented rules with severity and provenance
  • Semantic references — clock names, ports, pins resolved or honestly reported
  • Trust scope — every run reports what was and wasn't fully analyzed
02 / UNDERSTAND

Analyze structure

  • Clock intelligence — primary, generated, virtual; hierarchy and relationship matrix
  • Design context — netlist-aware object resolution when a netlist is supplied
  • Coverage — object-level evidence, bus-aware, never reduced to one number
03 / ASSESS

Assess quality

  • Constraint interactions — duplicates, overrides, contradictions, STA-review overlaps
  • Readiness model — seven dimensions with blockers, review items and actions
  • Honest status — READY is never presented as signoff
04 / PROTECT

Guard regressions

  • Snapshots & baselines — structured finding identity, not line-number diffs
  • Semantic readiness diff — NEW / RESOLVED / CHANGED / UNCHANGED
  • CI quality gates — BLOCKERS_ONLY → STRICT, deterministic exit codes
05 / PROVE

Show evidence

  • Verified release evidence — every benchmark number maps to a repo artifact
  • Clean-room install checks — the wheel, not the checkout
  • Trust Center — exactly what is validated, and what is not
THE BOUNDARY

What it is not

  • Not an STA engine — no timing propagation, slack, or .lib analysis
  • Not a signoff tool — READY ≠ timing closure
  • Not an LLM validator — deterministic and reproducible by design

The architecture

Deterministic by design

The validator is a fixed pipeline of parsers, checkers and analyzers. Same input, same output, every time — no model inference, no external API, no network dependency in the runtime.

✓No LLM required — validation never calls an AI model. AI may be used to develop the product; it is not part of runtime analysis.
✓Offline-capable — the wheel runs locally; clean-room checks verify no network imports.
✓Reproducible — structured findings, versioned snapshots, deterministic CI gates with exit-code contracts.
# one command, from checkout or installed wheel sdc-tools check design.sdc \ --netlist soc_top.v --top soc_top \ --baseline base.json --gate STRICT # machine-readable everywhere sdc-tools check design.sdc --json > result.json sdc-tools report check design.sdc --format html # exit codes: 0 pass · 1 fail · 2 invalid · 3 engine echo $? # → 0

Trust boundary

Precise about what it validates

Validates

SDC syntax and semantics, clock structure, semantic references, coverage, interactions, readiness and regression — within a documented support boundary.

Does not validate

Timing propagation, slack, delay calculation, .lib analysis, physical timing, timing closure or signoff STA. Those remain with dedicated STA engines.

Reports honestly

NETLIST_REQUIRED, TCL_EXECUTION_REQUIRED, UNSUPPORTED and NOT_VALIDATED constructs are surfaced — never silently assumed correct.
