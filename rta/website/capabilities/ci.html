Capability · CI Quality Gates

Constraint regressions blocked before merge

Deterministic policies, strict exit-code contracts, and a guarantee: engine failures never pass a gate. Vendor-neutral — any CI can call the CLI.

Policies

Four built-in gates, one CUSTOM escape

BLOCKERS_ONLY

Fail only when new blockers appear against the baseline. Advisories and warnings don't fail the gate.

NO_READINESS_REGRESSION

Fail when the overall readiness verdict degrades relative to the baseline, in addition to new blockers.

STRICT

Fail on any new error, warning or readiness degradation. The tightest built-in gate.

CUSTOM

Declarative policy data — no eval, no executable logic in the runtime. Verified by the security suite.

Exit-code contract

Deterministic and script-safe

0 gate passed
1 regression / disallowed change
2 invalid invocation (missing baseline, bad policy)
3 engine failure — never reported as pass

Example

# GitHub Actions is one example — any CI can call the CLI - name: Validate constraints run: rta check $SDC \ --baseline base.json --gate STRICT

The same command works in Jenkins, GitLab CI, or a local pre-commit hook — no vendor lock-in.

◈ What a gate pass does not mean. A green gate means no disallowed constraint-readiness regression under the selected policy — it does not mean timing will close. CI PASS ≠ timing pass.
