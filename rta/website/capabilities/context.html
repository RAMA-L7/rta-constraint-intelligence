Capability · Design Context

SDC-only, or SDC + structural Verilog

Supply a netlist and the validator resolves object references against real ports, pins, cells, nets and hierarchy. Skip it and references are honestly reported as netlist-required.

The problem

Object references are either proven or reported

get_ports / get_pins / all_* collections can silently match nothing, match the wrong object, or rely on hierarchy that doesn't exist. Design context turns "probably fine" into "resolved" or an explicit limitation.

What design context enables

  • Object resolution — references resolved against a structural inventory, or reported empty / unsupported
  • Hierarchy — module/instance tree with top-level ports and widths
  • Coverage evidence — object-level constraint coverage across inputs, outputs and buses
  • Trust upgrade — NETLIST_REQUIRED constructs become VALIDATED where they resolve

What it does not enable

✗No timing propagation — context is a structural inventory only
✗No slack or delay — no delay values, no .lib analysis
✗No signoff — a resolved object is not a correct constraint

Collection resolution

Resolved · Empty · Unsupported

StatusMeaningUser action
RESOLVEDreference matches real object(s) in the netlistnone — evidence captured
EMPTYcollection matched nothing (typo / missing object)fix the object reference
UNSUPPORTEDexpression outside the supported Verilog subsetreview manually; reported, not assumed
NETLIST_REQUIREDno netlist supplied for this runsupply structural Verilog + top module
◈ What design context does not mean. Structural resolution proves an object exists and is referenced — it does not prove the constraint on it is timing-correct. Coverage ≠ correctness.
