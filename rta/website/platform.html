Stages in detail

What happens at every step

Stage 01–02 · Input & Preprocess

Understand the file before judging it

The preprocessor normalizes SDC across Tcl variable resolution, comment stripping, multiline continuation and scientific notation — so identical constraints written differently are analyzed identically.

  • Tcl scalar variables resolved before analysis
  • Collection parsing (get_ports / get_pins / all_*) normalized
  • Commented-out constraints never create phantom clocks
# variables + multiline + sci-notation all normalize the same set CLK_PER 5.0 create_clock -name clk_core \ -period $CLK_PER [get_ports clk]
Stage 03 · Validation

Deterministic rules with provenance

The rule engine emits findings with a stable code (SDC-001…), severity, a human-readable message, and the exact source line. Findings are identity-stable for diffing — never fragile message matches.

  • 100+ documented rules across syntax, semantics, clocks, I/O and exceptions
  • Every finding: rule · severity · evidence · source line
  • Trust scope reports what was and wasn't fully analyzed
ERRORSDC-008 input delay 9.0ns ≥ clock period — no timing margin
L7 · set_input_delay -max 9.0 -clock clk_core [all_inputs]
WARNINGSDC-030 no input delay on data_in[7:0]
Stage 04 · Clock intelligence

Structure before timing

Clocks are parsed into primary, generated and virtual definitions; ancestry is inferred; every pair is classified synchronous, asynchronous, physically exclusive or logically exclusive — and compared against declared set_clock_groups.

  • Generated-clock hierarchy with divide/multiply and source node
  • Relationship matrix with declaration mismatch detection
  • Explicitly structural — no timing propagation is ever implied
Inferred relationship
SYNC clk_div2 ← clk_core (derived, /2)
ASYNC clk_core / clk_io (no common ancestor)
MISMATCH clk_core / clk_io declared async, inferred sync
Stage 05–06 · Context & coverage

Know what the constraints actually cover

With a structural Verilog netlist, object references resolve against real ports, pins, cells and nets. Coverage is reported per object and per bus bit — and always with the disclosure that coverage ≠ correctness.

  • Object resolution: resolved · empty · unsupported expression
  • Bus-level coverage strips with exact constrained ranges
  • Without a netlist, references are honestly NETLIST_REQUIRED
data_in[31:0] — partial coverage
31 ──── constrained ──── ════════ gap ════════ 0
■ constrained (31:12) ■ gap (11:4) ■ partial (3:0)
Stage 07–08 · Interactions & readiness

Conflicts first, then a defensible verdict

Constraint interactions are separated into provable conflicts (duplicates, overrides, contradictions) and STA-review overlaps that legitimately require path analysis. Readiness then aggregates everything into seven dimensions with blockers, review items and recommended actions.

  • Dual-line provenance for interaction findings
  • Readiness: CLOCKS · I/O · EXCEPTIONS · COVERAGE · CONSISTENCY · ANALYSIS_TRUST · DESIGN_CONTEXT
  • READY is a readiness verdict — never an STA signoff

Stage 09–11 · Snapshots, diff, CI

Regressions become reviewable events

Snapshots capture structured finding identity; a baseline diff classifies NEW, RESOLVED, CHANGED and UNCHANGED findings; CI gates turn policies into deterministic pass/fail with a strict exit-code contract.

  • Policies: BLOCKERS_ONLY · NO_READINESS_REGRESSION · STRICT · CUSTOM
  • Engine failures never pass a gate (exit 3 / invalid exit 2)
  • Vendor-neutral — any CI system can call the CLI
rta check design.sdc --baseline base.json --gate STRICT # exit 0 → gate passed · 1 → regression · 2 → invalid · 3 → engine # GitHub Actions is one option; any CI can call the CLI - run: rta check $SDC --baseline base.json --gate STRICT
